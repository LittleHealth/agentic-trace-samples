# FreeInference：三条会话与一周缓存分析

分析日期：2026-10-28。数据：2026-05-17 至 2026-05-23。所有结果来自 2026-10-28 完成的离线计算及原仓库模拟；没有调用大模型或重新运行轨迹中的工具。

[FreeInference 首页](../README.md) · [仓库首页](../../../README.md)

**结论：值得用于研究上下文增长、历史重复读取和缓存回收。** 一周 106 个顶层会话的 10,548 次请求中，tool 角色占累计输入 **56.66%**，相邻请求共享前缀占完整块输入 **89.89%**。官方模拟在 5 分钟 TTL 下，结合改写与结束信号回收后，缓存保留量按 token×时间累计减少 **46.78%**，命中率下降 **0.086 个百分点**。

**这些数据没有消息正文，不能验证语义压缩是否安全、NL2SQL 准确率是否不变。** tool 角色占比也不等于所有工具结果占比。四种回收策略来自官方代码，本次复现不构成新方法或创新性结论。

## 1. 三个会话：从哪里开始读

| 可读请求表 | harness | 请求数 | 输入 token：初始 → 末次 | session_id |
|---|---|---:|---|---|
| [持续追加](../01-append/README.md) | hermes | 44 | 10,421 → 45,790；峰值 45,790 | `38fd82c2b2f4693bcb97a6be528dccae` |
| [中途注入改写](../02-injection/README.md) | kilo | 27 | 15,531 → 30,651；峰值 30,651 | `d3cf2b494fbb04a8d1850c2367f5fcdd` |
| [删除历史轮次](../03-dropped-turns/README.md) | cline | 46 | 73,397 → 50,639；峰值 94,984 | `26b3e835fc1dc0d41af636b34005c880` |

每条样本都有：`trace.raw.json`（来源记录）、`trace.json`（完整缩进版）、`requests.json`（保留字段并附加指标，长块数组仅在此文件中替换为明确标注的摘要）、`requests.csv` 和逐请求 Markdown 表。完整块数组始终保留在 trace.json。这三个会话按变化方式选取，不能用于推断三类现象的发生率。

一次模型请求的顺序是：**已有上下文 → 模型请求 → 模型响应产生工具调用 → 工具结果 → 可能进入下一次请求**。表中“本次响应的工具调用”和“新工具结果 token”位于该行输入之后。一条请求不一定对应一个用户轮次，多个工具调用也可能属于同一请求。

| 字段 | 含义 / 阅读方式 |
|---|---|
| `step` / `turn_index` | 来源中的请求序号 / 用户轮次索引；阅读表另提供从 1 开始的请求编号 |
| `step_trigger` / `link_reason` | 新输入由 user 还是 tool 触发，以及与上一请求如何关联 |
| `start_ms` / `end_ms` / `ttft_ms` | 网关请求开始、完成时间及首 token 延迟 |
| `model` / `provider` | 模型名和匿名化供应商标签 |
| `role_tokens` | 用 o200k_base 统计的 system、user、assistant、tool 和工具定义输入量 |
| `provider_tokens` | 供应商报告的 prompt、completion、cached；与 o200k_base 不混算 |
| `mutation.transition` / `cause` | 来源标注的追加、改写、切换及原因；标签不证明语义已经无用 |
| `block_ids` | 16-token 链式前缀块 ID，用于精确前缀比较；不含可还原正文 |
| `tool_calls.name` / `arguments` | 工具名及匿名化参数骨架，`<path>`、`<str>` 为来源占位符 |
| `outcome` / `result_tokens` | 工具结果状态及结果 token 数，工具结果正文未发布 |
| `tool_calls.latency_ms` | 来源定义的至下一模型请求的间隔，不直接视为精确工具执行耗时 |

![三个会话的输入增长与相邻前缀复用](figures/01-three-sessions.png)

三个可核查的片段：

- **持续追加**：请求 1 输入 10,421 token，响应调用 terminal、cronjob，记录新工具结果 1,637 token。请求 2 输入增至 12,204，其中 tool 角色为 1,641 token，与上一请求共享 10,416 token。两个结果计数略有差异，不能把 result_tokens 机械等同于下一次输入增量。
- **中途改写**：kilo 的请求 3 被来源标为 injection，输入从 15,940 增至 16,091；即使总长度增加，也可能发生历史改写，而非纯追加。完整变化见逐轮表。
- **删除旧轮次**：cline 的请求 9 输入从 92,182 降至 64,016 token，但共享前缀只剩 12,848 token，约占当前完整块的 20.07%。请求 22、45 再次下降。这说明输入变短与缓存前缀保持是两个不同目标；记录本身不能证明删去的内容在语义上已无用。

cline 这条样本在存在 read_file 结果时 `role_tokens.tool` 仍为 0，而后续 user 角色输入增长。这说明角色计数不足以定位全部工具观察。没有正文时不能补算其精确语义占比。

## 2. 从单日到一周的结果

先分析本地 2026-05-17 的全部 25 个顶层会话，再保存[扩展判断](day/decision.json)：工具角色占比 40.58%、相邻共享前缀 88.04%、存在增长和改写，足以支持一周描述性分析。之后才下载该周其他日期和官方处理表。这个判断是探索性判断，没有设定统计显著性门槛。

一周文件包含 106 个顶层会话、19 个嵌套子会话。以上指标与官方 **Agentic** scope 一致，只统计顶层会话；该周没有 SWE-Bench 顶层会话。初始请求可能已带有长历史，因此“初始输入”是观测起点，不是任务真正开始时的空上下文。

tool 角色累计输入为 **540,579,979 token**，其中包含重复送入模型的旧结果；本周工具调用中有 **11,025/11,045** 条记录了 result_tokens，合计新工具结果 **6,316,617 token**。后者是另一种观测量，不用作历史重复次数的分母。共有 **453** 次 tool 触发请求的 tool 角色输入为 0，进一步说明角色统计有边界。

### 统计口径

对请求 $t$，令 $I_t$ 为五类 role_tokens 之和，$B_t$ 为有序 block_ids，$L_t$ 为 $B_{t-1}$ 与 $B_t$ 的最长公共前缀块数。

$$
R_{tool} = \frac{\sum_t I_{t,tool}}{\sum_t I_t},\qquad
R_{prev} = \frac{16\sum_t L_t}{16\sum_t |B_t|}.
$$

同会话历史重复率把分子换为当前输入中曾出现在该会话任意早先请求中的块数乘 16。每个会话首个请求的复用数为 0，仍计入分母。5 分钟内共享前缀指标要求当前请求开始距上一请求完成不超过 300 秒；它只检查相邻请求，不是完整缓存模拟。

两个复用指标覆盖整个输入前缀，包括可能重复的系统提示和工具定义；不能把复用量全部归因于对话历史，也不能由它们单独算出工具结果的重复占比。

这些是按累计 token 加权的比率，长会话权重更大，因此同时给出会话级中位数。块统计舍去每次输入末尾不足 16 token 的部分，本周合计 **79,228 token**，仅占输入 **0.01%**。ID 来自链式前缀哈希：早期内容变化后，后面的相同文本也可能获得不同 ID，不能用它查找脱离前缀的相同段落。

provider cached 另行保留：本周 **9,309/10,548** 次请求同时有 cached 与 prompt 报告，其供应商口径累计 cached/prompt 为 **89.30%**。缺失值没有按 0 处理；这个值不与模拟命中率直接相减。

**追加请求**有 9,076 次，其共享前缀累计占当前完整块的 **98.98%**；**改写请求**有 1,333 次，对应比例为 **26.79%**。这是分组相关性，不是控制实验。848 次 dropped_turns 标记中有 583 次输入确实下降；改写标签与输入缩短不能混为一谈。另有 33 次模型或供应商变化，真实缓存还可能受隔离边界影响。

## 3. 官方缓存模拟

已实际运行原仓库 `python -m simulation --week 2026-05-17`，使用 2 个进程，退出码 0。固定代码提交 `925a718eed7cc01255e7dcea024e70389cf021e5`，工作目录无源码修改；固定数据版本 `16d3c04dae6ccaa0c48a9064e204e3a8f1eb9ade`。所有处理表和 7 个原始日文件通过官方哈希检查。

| 官方策略 | 实际模拟什么 |
|---|---|
| `ttl_only` | 仅依赖 TTL 到期，不主动回收 |
| `reclaim_mutate` | 同会话下一次请求到达时，回收新输入中已不含的旧块 |
| `reclaim_dead` | 在该会话最后一次模型请求完成时发出回收信号 |
| `reclaim_both` | 结合上面两种信号，取较早者 |

每种策略测试 13 个 TTL，共 **52 组缓存结果**。下表展示 5 分钟、15 分钟和无过期三档；[完整 52 行 CSV](official-simulation-summary.csv) 保留全部原始计数及派生指标。

![官方缓存模拟：命中率与保留量](figures/03-official-cache.png)

在 5 分钟 TTL 下，reclaim_both 使总保留量减少 **46.78%**、其中后续无读取部分减少 **87.06%**，命中率代价为 **0.086 个百分点**。15 分钟 TTL 对应总保留量减少 **67.26%**、命中率代价 **0.121 个百分点**。这给出了本周的缓存回收空间；不能改写成“可以从模型上下文安全删除这些 token”。

更接近在线可获得条件的是**只使用已到达请求的改写信号**：5 分钟 TTL 的 reclaim_mutate 已使保留量减少 **43.06%**，命中率下降 **0.016 个百分点**。该数字不需要预知会话何时结束，但仍受下面列出的缓存模型假设约束。

### 模拟的实际意义与边界

- **回收缓存不改变发送给模型的上下文。** 未命中块重新计算即可；这里评估的是命中率与保留时间，不是删改输入后的回答准确率。
- `reclaim_mutate` 用已到达的新请求比较块，因此有可执行的观测依据；跨会话复用或后续恢复旧前缀仍可能带来额外未命中。
- `reclaim_dead` 使用离线已知的最后请求时间。仅从当前请求不能知道用户还会不会继续，实际系统需要显式结束信号或预测器；不能把此处结果视为已实现的在线终止识别。
- 官方模型按内容块共享缓存，**不按 model/provider 分开**，每周冷启动，容量无上限。它没有模拟有限显存下的 LRU 淘汰、跨周历史缓存或真实供应商隔离，因此命中率是该模型下的结果。
- 请求到达时读块、完成时写块；官方实现将与前一次读取重叠的请求视作可命中。这是模拟假设，不是实测网关行为。
- 无过期时保留量高度受观察窗口结束影响，“后续无读取”只表示本周内无后续读取。优先解释 5/15 分钟结果；不把无过期的大幅下降当作普适节省比例。

官方命令还生成了 63 行 cheaper-reads 价格模型结果，保存在[原始输出目录](official-simulation/2026-05-17_2026-05-23/)。这是附带的假设价格模型，没有实际执行上下文压缩，也不是实付账单，本报告不据此声称费用或准确率收益。

## 4. 对研究方向的判断

**适合继续做的事**：用此数据量化长历史反复读取、前缀破坏发生在哪些变化上，以及在线可获得的改写/结束信号怎样改善缓存回收。增长、工具角色输入和改写对前缀的影响都有可复核的计数，周级模拟也给出了明确的收益与代价。

**当前证据没有建立的事**：这些内容在语义上冗余、可安全删去；新压缩方法比已有方法好；Data Agent 有独特规律；删改上下文后 NL2SQL 正确率不变。该发布数据无法恢复用户问题、SQL、数据库结果或最终回答，不能单独回答这些问题。

与现有研究计划的衔接应当是：FreeInference 用于系统层面的动机和缓存权衡，DAB 的正文轨迹用于判断“哪些工具结果还会被计算使用”以及压缩后计算是否正确。若继续研究在线缓存回收，应先明确新增信号或算法相对官方四种策略的差别，不能把本次复现的策略归为新方案。
